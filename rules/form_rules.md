# 入力フォーム デザイン・UXルール

## 目的

このドキュメントは、Webアプリで入力フォームを設計・実装する際の共通ルールです。

フォームは見た目を整えることよりも、ユーザーが次の状態で入力を完了できることを優先します。

- 迷わない
- 入力で止まらない
- 間違いに気づける
- 修正方法が分かる
- 送信後に何が起こるか分かる

---

## 基本方針

### 1. 入力項目は必要最小限にする

入力項目が増えるほど、入力負担と離脱の可能性が高くなります。

フォームに項目を追加する前に、次を確認します。

- この画面で本当に必要な情報か
- 後から入力しても問題ない情報ではないか
- システム側で自動設定できないか
- 既存データから取得できないか
- 選択肢や初期値で入力を省略できないか

### 2. 見た目より分かりやすさを優先する

フォームの評価基準は、装飾性ではなく操作性です。

- 入力順序が自然である
- 項目名が明確である
- 入力方法が分かる
- 必須・任意が分かる
- エラーの原因と直し方が分かる

### 3. ユーザーに考えさせすぎない

可能な限り、自由入力より選択式を使用します。

ただし、選択肢が多すぎる場合や、回答内容を限定できない場合は自由入力を使用します。

---

# フォーム全体のルール

## 1. 入力項目は原則として縦一列に並べる

フォームは、上から下へ自然に入力できる1カラム構成を基本とします。

横並びは、次のように関係性が明確で、画面幅にも余裕がある場合に限ります。

- 姓・名
- 開始日・終了日
- 年・月
- 都道府県・市区町村

### 推奨

```text
氏名
[　　　　　　　　　　　]

メールアドレス
[　　　　　　　　　　　]

電話番号
[　　　　　　　　　　　]
```

### 非推奨

```text
氏名 [　　　　　]  メールアドレス [　　　　　]
電話番号 [　　　]  住所 [　　　　　　　　　　]
```

スマートフォンでは、横並びの項目を縦並びに変更します。

---

## 2. 入力項目は自然な順序で配置する

入力項目は、ユーザーが情報を思い出す順番や、作業を進める順番に合わせます。

### 例：ユーザー登録

1. 氏名
2. メールアドレス
3. パスワード
4. パスワード確認
5. 利用規約への同意
6. 登録ボタン

### 例：シフト作成

1. シフト名
2. 対象年月
3. 基本条件
4. 拡張条件
5. 確認
6. 作成

システム内部のデータ構造や、データベースのカラム順をそのままフォーム順序に使用しません。

---

## 3. ラベルは入力欄の上に配置する

項目名は、原則として入力欄の上に配置します。

```html
<label for="email">メールアドレス</label>
<input id="email" name="email" type="email">
```

ラベルを入力欄の左側へ配置すると、視線が左右に動き、スマートフォンでも読みづらくなります。

例外として、チェックボックスやラジオボタンの選択肢ラベルは、入力部品の右側に配置できます。

---

## 4. ラベル・説明・入力欄・エラーを1グループにする

各入力項目は、次の要素をひとまとまりとして扱います。

1. ラベル
2. 必須・任意表示
3. 補足説明
4. 入力欄
5. エラーメッセージ

```html
<div class="form-control">
  <label for="email">
    メールアドレス
    <span>必須</span>
  </label>

  <p id="email-help">
    ログインに使用するメールアドレスを入力してください。
  </p>

  <input
    id="email"
    name="email"
    type="email"
    aria-describedby="email-help email-error"
  >

  <p id="email-error" role="alert">
    メールアドレスの形式で入力してください。
  </p>
</div>
```

別の項目との間には十分な余白を設けます。

---

## 5. プレースホルダーは入力例にのみ使用する

プレースホルダーを項目名や説明文の代わりに使用しません。

### 推奨

```text
メールアドレス
例：user@example.com
[ user@example.com ]
```

### 非推奨

```text
[ メールアドレスを入力してください ]
```

プレースホルダーは入力開始後に消えるため、入力後も必要な情報はラベルや補足文として表示します。

---

## 6. 必須・任意を明確に表示する

必須項目と任意項目を、色だけに依存せず文字でも表示します。

```text
氏名　必須
備考　任意
```

全項目が必須の場合は、フォーム上部に次のように記載できます。

```text
すべての項目を入力してください。
```

必須項目にアスタリスクだけを表示する場合は、フォーム上部で意味を説明します。

```text
「*」は必須項目です。
```

---

## 7. フォーカス中の入力欄を明確にする

現在入力している項目が分かるように、フォーカス状態を強調します。

```css
input:focus,
select:focus,
textarea:focus {
  outline: 2px solid currentColor;
  outline-offset: 2px;
}
```

### 注意

- フォーカス表示を削除しない
- エラー色とフォーカス色を同じにしない
- 色だけでなく、枠線の太さやアウトラインでも区別する
- キーボード操作でもフォーカス位置が分かるようにする

---

## 8. フォーム内の補助リンクは入力内容を失わせない

利用規約やプライバシーポリシーなど、フォーム入力中に確認するリンクは、入力内容が失われない設計にします。

候補は次のとおりです。

- 別タブで開く
- モーダルで表示する
- 入力内容を自動保存する
- 戻った際に入力値を復元する

別タブで開く場合は、外部表示であることをユーザーに伝えます。

```html
<a href="/privacy/" target="_blank" rel="noopener noreferrer">
  プライバシーポリシー
  <span aria-label="新しいタブで開く">↗</span>
</a>
```

# 入力項目別のルール

## 9. 自由入力より選択式を優先する

回答内容をあらかじめ限定できる場合は、選択式を使用します。

### 選択式が適している例

- 性別
- 職種
- 役割
- 夜勤可否
- 曜日
- 都道府県
- ステータス
- 通知設定

### 自由入力が適している例

- 氏名
- メールアドレス
- 備考
- 問い合わせ内容
- その他の詳細

選択肢を増やしすぎて、かえって探しにくくならないようにします。

---

## 10. 選択肢には該当しない場合の選択肢を用意する

ユーザーに当てはまる選択肢がない可能性がある場合は、逃げ道を用意します。

### 例

- その他
- 未定
- 分からない
- 回答しない
- 相談したい
- 該当なし

「その他」を選択した場合だけ、詳細入力欄を表示する設計も有効です。

---

## 11. 選択肢が少ない場合はラジオボタンを使用する

3〜5個程度の選択肢は、ラジオボタンを優先します。

```text
夜勤の可否

○ 夜勤可能
○ 夜勤不可
○ 要相談
```

ラジオボタンは選択肢が最初から見えるため、ドロップダウンより少ない操作で選択できます。

### 使用条件

- 1つだけ選択する
- 選択肢が少ない
- 選択肢を比較する必要がある

---

## 12. 選択肢が多い場合はドロップダウンを使用する

選択肢が多い場合は、ドロップダウンや検索可能な選択UIを使用します。

### 目安

- 6件以上：ドロップダウンを検討
- 数十件以上：検索・絞り込み機能を検討
- 数百件以上：オートコンプリートを検討

最初の選択肢に、意味のある案内を表示します。

```html
<select name="job">
  <option value="">職種を選択してください</option>
  <option value="nurse">看護師</option>
  <option value="care_worker">介護士</option>
</select>
```

必須項目では、案内用の選択肢を送信可能な値として扱わないようにします。

---

## 13. チェックボックスは原則として縦に並べる

複数選択のチェックボックスは、1行につき1項目を基本とします。

```text
固定休日

□ 月曜日
□ 火曜日
□ 水曜日
□ 木曜日
□ 金曜日
□ 土曜日
□ 日曜日
```

選択肢が2〜3個で短い場合に限り、横並びも許容します。

### 実装上の注意

- ラベル全体をクリック可能にする
- 選択肢間に十分な間隔を設ける
- タップ領域を小さくしすぎない
- チェック状態を色だけで表現しない

---

## 14. ファイルアップロード条件を事前に明記する

ファイルアップロード欄には、アップロード前に制限を表示します。

### 表示する内容

- 対応形式
- 最大ファイルサイズ
- 最大ファイル数
- 推奨画像サイズ
- 縦横比
- パスワード付きファイルの可否

### 例

```text
プロフィール画像

JPEG、PNG、WebP形式
最大5MB
1ファイルまで
推奨サイズ：800 × 800px
```

アップロード後は、ファイル名・容量・プレビュー・削除ボタンを表示します。

---

## 15. 送信ボタンには具体的な動作を書く

「送信」「OK」「登録する」だけではなく、押した後に起きることが分かる文言を使用します。

### 推奨例

- アカウントを作成する
- 入力内容を確認する
- スタッフ情報を登録する
- 変更内容を保存する
- シフト作成へ進む
- この条件でシフトを生成する
- パスワード再設定メールを送る

### 非推奨例

- 送信
- OK
- 実行
- 次へ

破壊的な操作では、対象も明記します。

```text
このスタッフを削除する
シフトを初期状態に戻す
```

---

# 入力エラーのルール

## 16. エラー状態を一目で分かるようにする

エラー時は、次の複数の表現を組み合わせます。

- エラー色
- 枠線
- エラーアイコン
- エラーメッセージ
- `aria-invalid="true"`

```html
<input
  id="email"
  name="email"
  type="email"
  aria-invalid="true"
  aria-describedby="email-error"
>

<p id="email-error" role="alert">
  メールアドレスの形式で入力してください。
</p>
```

色だけでエラーを伝えないようにします。

---

## 17. エラーは該当項目の近くに表示する

エラーメッセージは、原則として対象の入力欄の直下に表示します。

```text
メールアドレス
[ abc ]

メールアドレスの形式で入力してください。
例：user@example.com
```

フォーム上部にエラー一覧を表示する場合でも、各入力欄の近くにもエラーを表示します。

長いフォームでは、上部のエラー一覧から該当項目へ移動できるようにします。

---

## 18. エラーメッセージは原因と修正方法を書く

ユーザーが次に何をすればよいか分かる文章にします。

### 推奨

```text
メールアドレスの形式で入力してください。
例：user@example.com
```

```text
パスワードは8文字以上で入力してください。
```

```text
対象年月は現在から12か月以内で選択してください。
```

```text
このメールアドレスはすでに登録されています。
ログインするか、別のメールアドレスを使用してください。
```

### 非推奨

```text
入力エラーです。
```

```text
正しく入力してください。
```

```text
不正な値です。
```

---

## 19. 入力途中ではエラーを表示しない

ユーザーが入力している途中で、即座にエラーを表示しません。

### 推奨する表示タイミング

- 入力欄からフォーカスが外れた時
- 選択が完了した時
- 送信ボタンを押した時
- 一定時間入力が止まった時

### 例外

パスワード条件や文字数制限など、入力中の案内が役立つ場合は、エラーではなく進捗・条件表示として扱います。

```text
パスワード条件

✓ 8文字以上
✓ 英字を含む
・数字を含む
```

入力が完了していない段階では、赤いエラーとして表示しません。

---

## 20. 入力前にヒントを表示する

ユーザーが入力方法を推測しなくて済むように、短い補足説明を表示します。

### 例

```text
シフト名

一覧画面で識別しやすい名前を入力してください。
未入力の場合は「2026年7月 シフト表」として保存されます。
```

```text
月休日数

スタッフ1人あたりの月間休日数を入力してください。
```

```text
固定休日

毎週必ず休みにする曜日だけ選択してください。
希望休は別画面で登録します。
```

説明文は長くしすぎず、詳細説明が必要な場合はヘルプやアコーディオンへ分離します。

---

# 状態別の表示ルール

## 通常状態

- ラベルが表示されている
- 必須・任意が分かる
- 入力例または補足説明がある
- 入力欄の境界が分かる

## フォーカス状態

- 現在の入力欄が強調される
- キーボード操作でも位置が分かる
- エラー状態と異なる見た目にする

## 入力済み状態

- 入力値が読みやすい
- ラベルが消えない
- 選択内容を確認できる

## エラー状態

- 対象項目が特定できる
- 原因が分かる
- 修正方法が分かる
- 入力済みの他項目は保持される

## 無効状態

- 操作できない理由を必要に応じて表示する
- `disabled` と `readonly` を目的に応じて使い分ける
- 無効状態を薄くしすぎて読めなくしない

## 読み込み状態

- 二重送信を防止する
- ボタンのラベルを状態に合わせて変更する
- 処理中であることを表示する

```text
シフトを生成しています…
```

---

# ボタンのルール

## 主ボタン

1画面につき、最も重要な操作を主ボタンとして扱います。

### 例

- 登録する
- 保存する
- 次へ進む
- シフトを生成する

## 副ボタン

キャンセルや戻る操作は、主ボタンより目立たせません。

### 例

- キャンセル
- 戻る
- 下書き保存

## 危険な操作

削除・リセットなどの操作は、通常の保存操作と区別します。

- 危険色を使用する
- 対象を具体的に書く
- 必要に応じて確認画面を表示する
- 元に戻せない場合は明記する

---

# アクセシビリティルール

## ラベルを必ず関連付ける

```html
<label for="staff-name">氏名</label>
<input id="staff-name" name="name" type="text">
```

## エラーと補足文を関連付ける

```html
<input
  id="password"
  name="password"
  type="password"
  aria-describedby="password-help password-error"
  aria-invalid="true"
>
```

## キーボードだけで操作できるようにする

- Tabキーで自然な順番に移動できる
- EnterキーやSpaceキーで操作できる
- フォーカス表示が消えていない
- 独自UIでもキーボード操作に対応する

## タップ領域を確保する

チェックボックス、ラジオボタン、アイコンボタンなどは、小さすぎるクリック領域にしません。

## 色だけで意味を伝えない

次の情報は、文字・アイコン・枠線なども併用します。

- 必須
- エラー
- 成功
- 選択中
- 無効状態

---

# レスポンシブ対応ルール

## スマートフォン

- 原則1カラム
- 横並び入力を縦並びに変更
- ボタンは押しやすい幅にする
- 画面端に十分な余白を設ける
- ソフトウェアキーボード表示中でも操作できる
- エラーメッセージが画面外に隠れない

## デスクトップ

- フォームの横幅を広げすぎない
- 長い入力欄が必要ない項目は適切な幅にする
- 余白によって項目のまとまりを示す
- 視線移動が増える多カラム構成を避ける

---

# 実装時の判断基準

## ラジオボタンを使う

- 1つだけ選択
- 選択肢が3〜5件程度
- 選択肢を比較して選ぶ必要がある

## チェックボックスを使う

- 複数選択
- ON・OFFの設定
- 利用規約への同意

## ドロップダウンを使う

- 選択肢が多い
- 一覧を常に見せる必要がない
- 画面をコンパクトにしたい

## トグルスイッチを使う

- 即時反映されるON・OFF設定
- 現在の状態を明確に示したい

保存ボタンを押すまで反映されない設定では、チェックボックスの方が自然な場合があります。

## テキストエリアを使う

- 複数行の文章を入力する
- 備考
- 問い合わせ内容
- 詳細説明

---

# フォーム作成時チェックリスト

## 項目設計

- [ ] 本当に必要な項目だけになっている
- [ ] 後から取得できる情報を最初から求めていない
- [ ] システム側で自動入力できる項目を手入力させていない
- [ ] 自由入力を選択式へ置き換えられないか確認した
- [ ] 選択肢に「その他」「未定」などの逃げ道がある
- [ ] 入力項目が自然な順序で並んでいる

## レイアウト

- [ ] 原則として縦一列になっている
- [ ] ラベルが入力欄の上にある
- [ ] ラベルと入力欄が視覚的にまとまっている
- [ ] 項目同士に十分な余白がある
- [ ] スマートフォンで横スクロールが発生しない
- [ ] フォームの横幅が広すぎない

## 表示

- [ ] 必須・任意が一目で分かる
- [ ] プレースホルダーをラベル代わりにしていない
- [ ] 入力例が必要な項目に表示されている
- [ ] 補足説明が短く具体的である
- [ ] フォーカス中の項目が明確である
- [ ] 無効状態でも文字が読める

## 選択UI

- [ ] 少ない選択肢にドロップダウンを使っていない
- [ ] 多い選択肢をラジオボタンで並べていない
- [ ] チェックボックスが見やすく並んでいる
- [ ] ラベル全体をクリックできる
- [ ] 選択状態が色以外でも分かる

## エラー

- [ ] エラーが該当項目の近くに表示される
- [ ] エラー原因が具体的に書かれている
- [ ] 修正方法が分かる
- [ ] 入力途中で不要なエラーを表示しない
- [ ] エラー後も入力済みの値が保持される
- [ ] 最初のエラー項目へ移動またはフォーカスできる
- [ ] エラーを色だけで表現していない

## ボタン

- [ ] ボタンの文言から次の動作が分かる
- [ ] 主ボタンが1つに絞られている
- [ ] キャンセルと主操作を区別できる
- [ ] 削除・リセットを通常操作と区別している
- [ ] 送信中の二重クリックを防止している
- [ ] 処理中の状態が表示される

## アクセシビリティ

- [ ] `label` と入力欄が関連付けられている
- [ ] キーボードだけで操作できる
- [ ] フォーカス表示が確認できる
- [ ] エラーが読み上げ可能になっている

# コードレビュー時の確認事項

フォーム関連のプルリクエストでは、最低限次を確認します。

1. 入力項目が必要最小限か
2. ラベルが入力欄の上にあるか
3. 必須・任意が明確か
4. 適切な入力UIが選ばれているか
5. エラーが項目の近くに表示されるか
6. エラー文が具体的か
7. 入力値がエラー後も保持されるか
8. スマートフォンで操作しやすいか
9. キーボード操作に対応しているか
10. ボタンの動作が文言から分かるか
11. 二重送信を防止しているか
12. 危険な操作に確認があるか

# 最終原則

フォーム改善の目的は、装飾を増やすことではありません。

ユーザーが次の状態で操作を完了できるフォームを目指します。

> 迷わず、止まらず、不安なく入力できること。

フォーム完成後は、開発者自身が最初から最後まで操作し、次の箇所を確認します。

- どこで入力方法に迷うか
- どこで説明を読み直すか
- どこで操作が止まるか
- どのエラーが理解しづらいか
- 送信ボタンを押す前に不安がないか

実際の操作で迷いが発生した箇所は、デザイン・文言・入力方式のいずれかを見直します。
